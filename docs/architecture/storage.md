# Saved connection storage contracts

## Implemented scope

The optional `profiles` Cargo feature enables `storage` and Serde/serde_json without
Tauri. `desktop` enables it. The ordinary library and protocol/session APIs are
unchanged. Profiles store only a name, endpoint and transcript appearance; no
credentials, commands, history, transcripts or automatic connection behavior.
The frontend keeps Custom values in memory only.

## Schema and bounds

`profiles.json` resides in the backend-resolved Tauri
[application configuration directory](https://docs.rs/tauri/latest/tauri/path/struct.PathResolver.html#method.app_config_dir).
No IPC command accepts or returns a path. Version 1 has this shape:

```json
{
  "version": 1,
  "nextId": 2,
  "selected": 1,
  "profiles": [{
    "id": 1,
    "name": "Local demo",
    "host": "localhost",
    "port": 4000,
    "appearance": {
      "fontSize": 14,
      "foreground": "#e6e8eb",
      "background": "#111318"
    }
  }]
}
```

Files are limited to 128 KiB, including whitespace. Reads retain at most that bound
plus one overflow-detection byte. There are at most 100 records. Names are trimmed
on mutation, nonempty, control-free and at most 128 UTF-8 bytes; uniqueness uses
exact, case-sensitive comparison after trimming. Stored names must already be
trimmed. Host and port use the existing endpoint validator: ASCII hostname or
IPv4/IPv6 literal and port 1–65535. Font size is an integer 10–24; colors are `#`
plus exactly six ASCII hexadecimal digits, case-insensitive. Defaults are 14 px,
`#e6e8eb` text and `#111318` background.

IDs and `nextId` are nonzero u64 values; record IDs are unique and strictly below
`nextId`. IDs are generated by the backend, never reused after deletion, and
counter exhaustion rejects creation. `selected` is null or references an existing
record. Profile IDs are unrelated to transient connection IDs. IPC represents
IDs as decimal strings to avoid JavaScript precision loss. Unknown fields,
duplicate JSON fields, invalid records/references, and unsupported versions reject
the entire file; there is no partial salvage or implicit migration.

## Ownership, admission and commit

One `ProfileService` owns the document and lock for the application. It admits
at most one operation with a nonblocking semaphore; further requests receive a
sanitized Busy category instead of entering an unbounded queue. Filesystem work
runs in `spawn_blocking`, under the storage mutex. The admitted operation retains
its permit through completion even if the IPC caller disappears. Shutdown closes
admission, awaits accepted work, and releases the lock alongside awaited session
cleanup. A hung filesystem can delay this shutdown; writes are not abandoned.

Loading attempts a nonblocking exclusive
[`File::try_lock`](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock)
on a separate `profiles.lock` file. Keeping the lock separate preserves ownership
across replacement of `profiles.json`. Another cooperating instance can read a
valid snapshot but cannot mutate it. Only explicit Retry loading attempts to
acquire a missing lock again. The lock is advisory on platforms with advisory
locking; external editors must close the app before editing its file. The empty
lock file can remain after exit: file existence does not mean the lock is held.

Every mutation validates a cloned candidate document and its encoded byte size
before touching the destination. It exclusively creates a uniquely named temporary
file in the same directory, writes, flushes, synchronizes and closes it, then
renames it over `profiles.json`. The committed in-memory state is published only
after successful replacement. Pre-commit failure leaves the prior destination
and in-memory state intact and attempts to remove only its own temporary file.
Orphan temporary files from interruption are ignored, never treated as profiles.
There is no background retry of writes and no fallback that truncates the original.

Atomic replacement depends on the underlying filesystem's rename behavior.
Synchronizing file contents does not promise power-loss durability of directory
metadata: the parent directory is not synchronized. Network/removable filesystem
semantics and Windows replacement behavior require platform acceptance; this
slice's runtime evidence is macOS only. Failed replacement is a reported error,
not permission to delete the previous file.

## Failure and recovery

A missing file means an empty document. Malformed, oversized, unsupported-version,
unreadable files or unavailable paths remain untouched, disable writes, and
produce a persistent warning. Manual connections and session-only Custom appearance
remain usable. A failed reload retains the last valid in-memory snapshot as
read-only. Retry loading revalidates disk state and retries lock acquisition; it
never resets, backs up, renames, deletes or repairs an existing profile file.
There is no automatic migration or destructive recovery. See
[manual recovery](../development/setup.md#saved-connections-and-recovery).

Errors are payload-free categories with fixed Debug/Display descriptions. Native
DTOs are separate from storage types and share main-window/origin authorization
with the connection commands. The narrow commands are `load_profiles` (also Retry),
`create_profile`, `update_profile`, `update_profile_appearance`, `delete_profile`
and `select_profile`. Only the validated connection command starts network work;
no storage operation resolves a hostname or opens a socket.

## Selection and appearance

The frontend applies a saved selection immediately, then remembers its ID through
an explicit mutation. A failed preference write keeps the chosen values usable
and explains that the selection was not remembered; **Remember selection** retries
only on user action. Selecting Custom clears the persisted preference. Endpoint
edits switch to Custom without modifying a saved record. Deleting the selected
record commits first, then switches to Custom while retaining displayed values.
Create selects its newly committed record. Other updates preserve the selected ID.

Startup may restore the last saved selection only before local interaction.
Endpoint edits, connection start and opening an editor invalidate restoration;
a late response can refresh available records but cannot overwrite those values
or an active connection. A subsequent launch with no saved selection starts at
localhost:4000 with default appearance. No selection ever auto-connects.

Profile switching, creation, deletion and endpoint/name editing are disabled
while connecting, connected or disconnecting. Appearance remains editable. Valid
appearance drafts preview immediately; Cancel or Escape restores the prior
appearance. Save publishes saved-profile changes only after backend acceptance;
failures keep the dialog draft and preview. Custom's **Apply** is session-only;
**Save as** is required for persistence. Reset to defaults only changes the draft.

Appearance uses transcript-scoped CSS variables and distinct default/ANSI classes.
Explicit ANSI black/white remain fixed; inverse defaults use the configured
foreground/background in their reversed roles. Retained and incoming output
change together without mutating the model. Font changes preserve the retained
visible line, bottom-follow behavior and existing retention bounds. The inherited
font probe triggers the existing measured/debounced NAWS path. Command styling,
mask protection and connection state are unaffected. This is approximate text
layout, not terminal cell-width emulation.
